# 商城轉檔、ECOUNT 銷貨與理貨回匯

本功能先在 DEV 驗收：https://corely-wms-dev-249593319772.asia-east1.run.app/admin/marketplace-converter 。正式站不隨 DEV 更新。行政使用拋單員、管理員或最高管理員；揀貨員及裝箱員不能存取轉檔 API 或保存的訂單金額。

## 作業流程

1. 從商城匯出**原始訂單明細**，不要先合併商品。Shopify 使用訂單 CSV；1Shop 使用訂單 Excel；SHOPLINE 使用包含商品貨號、數量、單價、訂單金額及付款／出貨狀態的訂單報表。
2. 登入 DEV → 出貨管理 → 開啟轉檔。三平台共用一個區塊，每次放入一個平台、同一店鋪的檔案。
3. 系統依表頭辨識，顯示原檔及本批納入數量。已付款且未出貨、或已辨識的貨到付款且未出貨可納入。Shopify 的 custom 依公司確認視為貨到付款；其他非貨到付款的未付款、已出貨、取消、退款或不明狀態會排除。僅兩筆已授權的 1Shop TST 訂單可用專用勾選納入未付款測試。
4. 核對下表設定，再按「保存並下載 ECOUNT 銷貨檔（27 欄）」。此時會保存轉檔批次及來源明細，**尚未建立揀貨任務、尚未送出 ERP 銷貨，也不扣庫存**。
5. 將下載的 27 欄檔案交由 ECOUNT 銷貨匯入，使用已配置的「銷貨匯入商城訂單」格式。核對公司、客戶、工業店倉庫、稅別、金額及品項後才完成銷貨。K 欄追蹤碼可用來查找該次轉檔，不能靠重下載判斷 ERP 是否已入帳。
6. 從 ECOUNT 匯出包含下方來源欄位的**理貨明細**。商品彙總報表已失去子訂單分配，不能作為這個回匯檔。
7. 回 DEV 的「已保存的轉檔批次」，在對應批次按「匯入理貨單」，上傳 ERP 理貨明細。系統核對整批訂單、來源明細、品項、數量及已確認條碼，一致後才一次建立各商城工作單。
8. 成功後按「查看理貨批次」看整批商品總表；按「批量列印工作單」取得每個商城子訂單的紙本。紙本有商城訂單號、ERP 批次、商品名稱、SKU、國際條碼、數量，以及提供時的 SN。
9. 倉庫先依整批商品總表預揀，再分配到各子訂單。人員在工作台選「揀貨」，掃紙本 **WT 工作單條碼（CODE128）**認領、帶出商城訂單並綁定登入者，再刷商品條碼／SN 核對。這個工作碼與商品條碼用途不同，也避免跨平台同名訂單誤認領。
10. 揀貨完成後，裝箱人員選「裝箱」，掃同一工作碼認領，再次核對。既有 SN、錯碼恢復、權限、例外處理及標籤列印流程保留；倉內完成不代表已交物流。此次不新增物流建單或印表機自動列印。

## 行政需要填／核對的欄位

| 畫面欄位 | 填入／確認內容 | 去向 |
|---|---|---|
| 商城店鋪 | 公司固定採用的店鋪名稱，回匯必須一致 | ECOUNT O；WMS 配對鍵 |
| ECOUNT 客戶／供應商編碼、名稱 | 依會計指定應收對象及 ECOUNT 主檔確認；不能以消費者訂單號代替客戶碼 | C、D |
| 發貨倉庫編碼 | 工業店已觀察為 003；實際操作前確認公司與倉庫 | G |
| 銷貨日期 | 本次 ERP 要入帳的日期 | A |
| 銷貨分組序號 | 本檔屬同張銷貨單時維持同值，預設 1 | B |
| 銷貨追蹤單號 | DEV 自動產生 TEST- 開頭、不超過 20 字的追蹤碼 | K |
| ECOUNT 品項編碼／名稱 | 從來源 SKU 提示開始，對照主檔後確認 | L、Q |
| 國際條碼 | 依實物或商品主檔核對；不能因 SKU 是 13 碼就認定相同 | 保存供 WMS 回匯核對，27 欄銷貨檔不另送條碼 |
| 商品分類 | 團購／團組名稱等分類 | 轉檔核對表；不會自動改 ECOUNT 商品分類主檔 |
| 幣別、稅制 | 本次僅 TWD、ECOUNT 稅類 11、含稅單價；須核對後勾選 | H、V；I 留空使用既有本幣設定 |
| 折扣分攤確認 | 訂單未分到商品的折扣按商品折後金額比例分攤，尾差按最小貨幣單位分配；原始金額仍保留 | V 及成交核對表 |
| 組合商品確認 | 1Shop 原檔已在主商品計價、元件未分價時，確認元件零元但仍出貨 | 元件數量保留 |
| 運費品項 | 核對 ERP 00001 運費為非庫存／數量管理除外 | 單獨金額列，不計入預揀 |

平台、商城訂單號、來源明細號、數量由系統產生或讀取，不能人工刪除或重新編號。原始檔含不能精確核對的金額、非零另列稅額、非整數數量或無法表示為分的單價時，會停止銷貨檔產生。

## ECOUNT 回匯欄位與配對

必須保留：理貨單號、商城訂單編號、平台、店鋪、來源明細號、品項編碼、品項名稱、國際條碼、數量；有 SN 時另保留「序號/批號」，不能留在摘要中。已觀察的 ECOUNT 公司／日期抬頭及末端匯出時間可保留。

- 27 欄銷貨檔：M=商城單號、N=平台、O=店鋪、P=來源明細號、L=品項、T=數量、V=含稅單價。
- WMS 使用「平台＋店鋪＋商城訂單號」找保存的訂單，再逐列比對「來源明細號＋品項＋數量＋已確認國際條碼」。理貨單號只用來建立倉庫批次，不取代商城訂單號。
- 運費必須對上保存的非庫存明細，且品項、數量、理貨單號一致，才排除出倉庫商品。未知空條碼商品仍阻擋，不能一律把空條碼列當運費。
- 從某轉檔批次進入回匯時，必須包括該批全部訂單。若 ECOUNT 合併了不同平台的多個已保存轉檔批次，從一般「出貨管理 → 匯入出貨單」上傳；系統可自動配對多個轉檔批次，但已匹配批次必須完整，不能混入未匹配的訂單。
- 已建立工作單的商城訂單，不會因換理貨單號再次建立。舊式未經轉檔的理貨檔仍沿用既有匯入方式；新流程請從保存的批次進入，避免失去配對檢查。

## 金額與紙本用途

轉檔保存每筆訂單原始金額及 ECOUNT 分攤後金額，下載「預揀與金額核對表」有五張工作表：預揀總表、訂單金額核對、來源商品對照、本批納入與排除、ECOUNT 成交核對。

商品預揀按 SKU／國際條碼加總；銷貨資料仍保留每筆商城明細與金額，不把不同成交價的訂單合成一筆銷售。Total 是來源訂單總額，COD 尚未收款；不等同實際入帳、金流撥款或扣除費用後金額。本次不自動寫收款沖銷或 ERP 會計分錄。

不保存原始檔內消費者聯絡資料、付款參考碼或地址；紙本用於商品揀貨／裝箱核對。物流收件標籤仍使用既有配送資料與流程。

## 驗收與已知限制

- 以實際 Shopify CSV 唯讀核對：50 筆原始訂單／63 商品列；本批 27 筆、33 商品列、38 件，訂單總額與轉出合計皆為 NT$35,852，未把這些真實訂單寫入 ERP／WMS。
- 1Shop 已提供的兩筆 TST 格式沿用既有解析與組合元件規則。拖把桿 4711299271137 主檔條碼空白；仍待實物／主檔確認，不能推定國際條碼。
- SHOPLINE 一般明細的明確欄名已支援，合成檔測試通過；尚未取得公司實際匯出檔。客製報表、組合主／子商品結構不能視為已驗收，未知格式會停止並提示。
- 已保存批次不直接覆寫；若對照或會計設定需更正，先停止 ERP 銷貨，交管理員核對處理。原始相同資料重試會讀回同一批；修改後重送同訂單會阻擋。
- 最終 ECOUNT 實際扣庫存、會計稅額及真實紙本掃描驗收仍需在已授權 TEST 範圍完成，程式及合成測試通過不能代替這項驗收。

官方欄位參考：[Shopify 訂單匯出](https://help.shopify.com/en/manual/fulfillment/managing-orders/exporting-orders)、[SHOPLINE 訂單報表](https://support.shoplineapp.com/hc/zh-tw/articles/115001459203)。欄位可依平台報表設定不同，實際輸入需通過本系統格式檢查。
