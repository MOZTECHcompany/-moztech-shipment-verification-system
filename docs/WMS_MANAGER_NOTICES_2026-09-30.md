# 管理員分工、雙向通知與異動明細

## 權限與操作

| 能力 | 訂單管理員 | 倉儲管理員 |
| --- | --- | --- |
| 拋單、提出數量／SN 異動、申請刪除 | 可以 | 可以 |
| 填寫尚未審核的例外處理方式 | 可以 | 可以 |
| 核准、駁回、結案及現場揀貨／裝箱 | 不可以 | 可以 |
| 收到另一方的異動通知 | 可以 | 可以 |

lemon 保留 `admin / orders`，mozwen（陳怡玟）保留 `admin / warehouse`。分工不是取消管理員身分。既有 `all` 相容選項顯示「跨部門管理員（訂單＋倉儲）」；既有帳號分工不會自動更動。新增管理員預選訂單分工，只有最高管理員可指派管理員分工。

訂單異動與刪除先送審，核准才套用，待審時原有作業阻擋持續有效。雙方管理員均可填寫一般例外的處理提案；一般例外核可／結案仍沿用原流程，不代表自動改庫存或退款。

## 改動

- 所有訂單、倉儲、跨部門管理員與最高管理員均接收異動送審、核准、駁回、結案、作廢、新品不良 SN 更換通知；原拋單人、申請者及指定揀貨／裝箱員仍保留。發起人不收到自己的警示音，無關的其他作業員不新增收件權限。通知與審核權限分開判定。
- 大型警示與訂單留言顯示操作人和分工、品項、條碼、前後數量、增加／移除的 SN、作廢前狀態；一般例外顯示處理方式、說明與前次處理內容。長明細可展開。聲音、知悉、斷線補取沿用既有通知流程。
- 明細在事件交易內封存到既有 JSONB payload；申請用當時 baseline，核准用 applyResult，絕不用現在的訂單數量倒推舊通知。同條碼連續減一再加一顯示兩段實際差異。舊通知沒有明細則維持既有呈現，不猜補歷史。
- 修正訂單作業頁漏掉兩種管理員的「填寫處理方式」按鈕，保留倉儲端審核限制，操作按鈕置於明細下方避免擠窄文字；處理內容標題對應真正狀態，不再固定稱為拋單員／待審核。
- 成員編輯表單按目標帳號重新初始化，避免前一人的姓名／角色／分工殘留；儲存等待真正 API 結果。新增／編輯角色欄位有清楚標籤和分工說明。

## 驗證與部署界線
