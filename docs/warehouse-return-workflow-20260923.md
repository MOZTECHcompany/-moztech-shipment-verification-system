# 商城回匯與倉庫作業（2026-09-23）

## 日常路徑

1. 商城訂單轉檔：保存來源訂單並下載 ECOUNT 銷貨檔。
2. 業務在 ECOUNT 儲存銷貨並確認庫存／會計結果，匯出理貨或出貨明細。
3. WMS「出貨管理 → 匯入理貨／出貨單」：自動找到來源批次並核對商品、數量、來源編號與已確認條碼；成功後建立整批預揀任務。
4. 工作台整批任務：主管一鍵列印預揀總表與全部訂單明細，記錄領單人，指派預揀人員。
5. 預揀人員查核商品與數量，完成後才放行各筆訂單。揀貨及裝箱仍是各自認領、掃码核對的獨立階段。

列印記錄代表領單與開啟列印作業；瀏覽器不能證明實體印表機已出紙。紙本含每筆 WT 工作條碼與商品條碼，完整列印不依畫面分頁。

## 回匯契約

- 理貨／出貨單需有 ECOUNT 實際單號、平台、店鋪、商城訂單編號、來源明細號、品項編碼、數量。
- 既有欄位別名可辨識。彙總銷貨保留批次號及 AG 來源分段，不可改成商品名稱猜配。
- 檔案內有國際條碼時逐列核對；沒有時使用原批次已確認條碼，未確認則阻擋。
- 原生序號／批號與既有摘要 SN 格式共用原解析規則；彙總 SN 依已保存的來源分配回每筆訂單。
- 必須包含全部實體商品；非庫存運費可不在理貨檔出現，若有則仍須核對。
- 有任一金額欄時，稅前、營業稅、含稅欄必須齊全且逐列一致。僅有物流資料時只記商品數量核對，不宣稱 ERP 金額已驗證。
- 同檔重試回傳原任務；不同內容、錯批、重複列、缺漏或數量不符均不覆蓋原結果。
- 一般非商城的原有匯入仍可使用。商城回匯不得使用 WMS 產出的上傳檔冒充 ERP 成功回執。

## 實作與驗證

- 統一 `/api/orders/import` 與原匯入 UI；取消批次詳情的重複上傳表單。
- 工作台整批任務卡、角色／指派範圍、即時更新；預揀未完成的子訂單不混入一般待揀清單。
- 一鍵列印完整總表與每筆訂單；保留原領單人、重印、併發及操作紀錄。
- 修正登入後 token 尚未寫入 localStorage 時導致批次永久載入的時序問題。
- backend 276 tests、frontend 271 tests、warehouse PostgreSQL 8 tests、warehouse parity PostgreSQL 32 tests 通過；前端 production build 通過。
- CUA 實際本機瀏覽器：原入口上傳 → 成功任務連結 → 工作台整批卡 → 一鍵列印內容（總表與 2 份明細）→ 主管指派 → 揀貨員登入／查核 3 件 → 完成預揀／兩筆待揀訂單。另驗證重新登入直接回到批次正常載入。
- 列印測試檢查 75 筆來源訂單全部出現在同次紙本內容，不受分頁限制。
- 可選 Playwright harness 已配合新入口調整，本次未執行；瀏覽器實測使用 CUA。

## 發布邊界

僅 DEV，無新增 migration；不變更現有人員／角色，不連正式資料庫測試，不提交 ECOUNT 銷貨。本機一次性資料不進 DEV。
正式 ECOUNT 匯出欄位、真實三平台來回、實體印表機及掃碼槍仍需現場驗收。資料缺來源編號時不能以 UI 放寬取代核對。
